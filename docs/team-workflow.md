# DeadCodex 六人协作规范

## 协作目标

本规范用于让六名成员在模块边界清晰的情况下并行开发，并确保每个合并项都具备测试、文档和可回滚记录。模块负责人对接口稳定性负责，但所有重要变更至少由另一名成员审查。

## 角色与所有权

| 成员 | 端到端任务包 | 主责生产代码 | 估算 |
|---|---|---|---:|
| A | 解析与 AST 信息采集 | `parser.py`、`collector.py`、扫描阶段 | 34 h |
| B | 领域模型与分析基础 | `model.py`、`scope.py`、`project.py`、`analysis.py`、`pipeline.py` | 34 h |
| C | 导入与引用解析 | `resolver.py`、解析契约 | 34 h |
| D | 控制流、调用图与项目可达性 | `reachability.py`、`callgraph.py`、项目分析阶段 | 34 h |
| E | 配置、CLI 与框架入口 | `config.py`、`adapters.py`、`main()` | 34 h |
| F | 报告、Baseline 与可交付工程 | `reporters.py`、`baseline.py`、`report()`、打包和 CI | 34 h |

详细到类、方法、测试文件和验收标准的任务清单见 [team-workload-plan.md](team-workload-plan.md)。`core.py` 按方法分配，不作为 F 的单人任务；测试、模块文档和答辩内容也由各模块负责人完成。

跨模块接口变更需要在 Pull Request 描述中列出调用方和迁移方式。负责人不应在未通知调用方的情况下更改字段语义。

## 分支与提交

- 每项任务从最新主分支创建短生命周期分支。
- 分支名使用 `feature/模块-任务` 或 `fix/模块-问题`。
- 一个提交只表达一个可解释的修改目的。
- 不提交 `.venv`、`.tox`、coverage HTML、临时报告或生成的 egg-info。
- 合并前保持测试通过，不使用破坏历史的共享分支强制推送。

## Pull Request 模板要求

每个 Pull Request 应回答：

1. 解决了哪个需求或缺陷。
2. 修改了哪些公共接口。
3. 默认行为是否变化。
4. 增加了哪些测试。
5. 有哪些已知限制和回滚方式。
6. 是否需要更新 Demo、README 或课程报告。

## Definition of Done

任务只有同时满足以下条件才算完成：

- 实现与需求验收标准一致；
- 新代码具有正常、边界和失败路径测试；
- 原测试全部通过；
- Ruff 检查与格式检查通过；
- 公共 CLI 或 API 变更已写入 README；
- 架构边界变化已写入 `docs/architecture.md`；
- 至少一名非作者完成 Code Review；
- 合并后 CI 通过。

## 接口联调顺序

```text
A 交付 AST 事实 -----> C 交付导入和引用目标 -----> D 交付调用边和可达性
       |                    ^                         ^
       v                    |                         |
B 交付模型、作用域和项目索引 -------------------------+
                                                    |
E 交付配置、CLI 和框架入口 ---------------------------+

B/D 交付分析结果 -----> F 交付报告、Baseline、打包和 CI
```

每个阶段提供最小固定测试夹具，下游不应依赖尚未公开的内部字段。

## 测试责任

- 模块负责人编写单元测试。
- 下游负责人编写接口契约测试。
- A 负责 AST 和原行为回归；B 负责模型与项目；C 负责导入与引用；D 负责两类可达性；E 负责配置、CLI 和框架；F 负责报告、Baseline 和安装交付。
- F 组织完整验收，但失败用例和覆盖率缺口由对应模块负责人修复。
- 每个人提交自己模块的文档与示例，F 只做交付文档汇总。
- 合并前由非作者检查失败路径和兼容路径。
- 每周至少一次运行完整 tox，避免只在源码路径下测试。

## 建议迭代安排

| 周次 | 主要目标 | 集成里程碑 |
|---|---|---|
| 1 | 阅读原项目、冻结需求、确定接口 | 原测试可运行 |
| 2 | Parser、Collector、Model、Project | 单文件模型贯通 |
| 3 | Import Resolver、Reference Resolver | 跨文件引用贯通 |
| 4 | Call Graph、Reachability | 项目入口到调用边贯通 |
| 5 | Flask/FastAPI、Reporter、Baseline | 完整用户流程贯通 |
| 6 | CI、Demo、文档、答辩 | 全量验收完成 |

## 风险升级机制

遇到动态语义无法静态确认时，应增加 unresolved 或 ambiguous 状态，不通过猜测产生唯一目标。公共接口冲突由 B 和相关模块负责人共同决定；范围外功能进入后续清单，不阻塞第一版验收。
